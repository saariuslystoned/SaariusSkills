# Codex Coordinator

Read the current request and trusted repository instructions first. Before applying this core, check those instructions and available skill metadata for a configured operator or repository profile. If they identify a profile-specific installed variant of this skill or an optional binding, read it first unless already loaded. Do not use an unbound core to bypass that profile, invent a binding, or search unrelated files. With no configured profile, use the portable workflow below. A profile or binding does not grant authority to act.

Coordinate the approved project through its existing task and execution tools. Do not create a scheduler, queue service or competing source of truth. Use `smoky-maintainer` for portfolio selection and `smoky-worktree` for source isolation. Model, effort, tool and review choices come from the current assignment and supported runtime; this skill supplies no fixed model roster.

## Prepare and route

Record the owner, outcome, scope/exclusions, source identity, acceptance criteria, dependencies, available capacity, repair budget and stop condition. Keep product targets and permissions in the project brief. Load only role-relevant skills and give each worker a compact assignment, not the full coordinator history. Selective context is not access isolation.

Qualify the next ready item against current evidence and overlapping work. Delegate only when the task authorizes the available mechanism; keep exactly one writer per conflicting target. Separate implementation from independent proof/review when required. Empty capacity is acceptable when no useful approved work is ready.

When the evidence shows a reproducible handoff loss, repeated avoidable
question, or recurring workflow repair with measurable acceptance, use
`harness2` as the refinement route: check active/completed experiment identity,
capacity, authorization, and runtime qualification, then delegate one bounded
experiment while product delivery continues. Read
`../harness2/SKILL.md`; its blocked/pending route applies when the separate
runtime integration is not qualified. Do not route ordinary product bugs,
unresolved preferences, provider outages, or authority gates through Harness².

## Follow through

Observe an assigned run to a terminal result without redispatching it. Before replacement or fallback, confirm termination or cancellation, inspect the current target and preserve partial artifacts. Timeout or missing output does not prove that a writer stopped. Transfer ownership explicitly.

Inspect the returned diff and evidence, apply the bounded repair budget, and continue other ready work while a dependent item waits for approval. If the assignment requires a PR, complete its required proof and review path; a narrower task can end at its stated artifact. Never convert clean checks into merge or deployment authority.

## Worker handoff

Include task/outcome; target and exact revision; allowed actions/files; acceptance and proof; writable owner; relevant skills; communication channel; next gate and stop condition. Obtain acknowledgement before dependent mutation. A staged message is not delivery, and an unacknowledged pause is not confirmed cancellation.

Require status, actual target/version, changed artifacts, checks/proof, unresolved findings, mutations performed, ownership state and one next action. Bind repository reviews to exact base/head; changed inputs invalidate prior terminal evidence where the review contract requires it. Report blocked channels honestly rather than claiming another worker stopped.

Use the repository's existing review and publication policy. Follow current authorization for external messages, shared documents, consequential actions and all merges. The coordinator owns the next decision, not unlimited permission to act.
