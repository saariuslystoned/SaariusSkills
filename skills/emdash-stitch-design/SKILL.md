# EmDash Stitch Design

Pair GrillTrack's product/visual decision loop with the official **Google Stitch CLI (`@google/stitch`)** and `ai-shed`'s **`stitch-mcp` server** (`https://stitch.googleapis.com/mcp`, backed by macOS Keychain `google-stitch`) to design and upgrade EmDash Astro websites without losing server-rendered CMS contracts or `FEATURE_MAP.md` verification hooks.

## Core Loop: GrillTrack ↔ Stitch CLI / MCP ↔ EmDash

1. **Grill & Lock Visual Intent (`grilltrack` + `design.md`):**
   - Before generating screens, read the target repo's `design.md`, `FEATURE_MAP.md`, and `.grilltrack/ledger.json`.
   - Use GrillTrack to lock the atmosphere, density, variance, typography posture, and non-goals (e.g., no invented checkout/cart controls on catalog-only slices).
   - Synthesize a semantic `.stitch/DESIGN.md` following [references/taste-and-prompts.md](references/taste-and-prompts.md).
   - **This skill carries method, not a look:** every palette, typeface, surface, shadow, and control placement comes from this site's own grill locks, recorded in its `design.md`, `.stitch/DESIGN.md`, and `tokens.css`. When distilling lessons from a run back into this skill, keep the method and leave that run's locked values in its own repo. Write each defect a run exposed as its own named rule with a mechanical check, both in the step it belongs to and in the closeout checks. A generic "re-read and confirm" step does not catch defects it does not name.

2. **Snapshot the Verified Real Page into Stitch (`stitch capture` + `stitch upload`):**
   - Check auth readiness via `stitch_status` (MCP) or `STITCH_API_KEY="$(security find-generic-password -s google-stitch -w)" stitch status --json` (CLI).
   - Discover routes with `stitch capture routes`, then start the real EmDash Astro server and capture self-contained rendered HTML for the target route using the official CLI:
     - Live URL capture, waiting for a selector that appears once the route has rendered: `stitch capture http://localhost:4321/cart --wait-for="<ready-selector>" -o .stitch/captures/cart.html --json`
     - Interactive Chrome DevTools tab capture (without reloading): `stitch capture --tab -o .stitch/captures/cart.html --json`
   - Create or select the Stitch project (`stitch find projects --json` / `stitch create project --title "<title>" --json` or MCP `list_projects` / `create_project`).
   - Upload and apply `.stitch/DESIGN.md` as a first-class Stitch Design System via `stitch upload design .stitch/DESIGN.md --project <project-id> --apply --json`, and upload the captured route HTML via `stitch upload screen .stitch/captures/cart.html --route /cart --title "Cart" --project <project-id> --json` (or `stitch_upload_file` via MCP).
   - Upload page captures as **desktop** screens (`deviceType: "DESKTOP"` on `screens:batchCreate`) whenever your upload route can set it. Uploads without a device type make Stitch give their variants phone-width canvas placeholders that overlap their neighbours ([stitch-sdk#383](https://github.com/google-labs-code/stitch-sdk/issues/383)). The CLI's `upload screen` has no device option yet ([stitch-sdk#384](https://github.com/google-labs-code/stitch-sdk/pull/384)).

3. **Walk the Complete Surface Checklist (One Variable / Surface at a Time):**
   - Build the checklist from the site's real routes (`stitch capture routes`) and its shared chrome. Never compound multiple visual variables in one round. When implementation starts depends on how the grill runs; see **Choose When to Build** below. For a storefront the checklist is typically:
     1. **Global Foundations (`design.md` + `tokens.css`):** Homepage Layout Architecture (`/`) → Color Palette (holding chosen layout constant) → Typography Role System (holding chosen layout + palette constant). Explore layout with generated variants. Run the palette and type rounds as deterministic HTML uploads with explicit CSS values, never as generations: uploads hold every other lock exactly and leave the generation budget for layout exploration and surface rounds. Before the first round, read the values the repo pins ([references/grilltrack-visual-cycle.md](references/grilltrack-visual-cycle.md) §5) and build them into every candidate, varying only what is free. A round whose candidates differ on a pinned value is decided by the pin, not compared.
     2. **Core Storefront Pages:** Product Detail Page → Category Collection Page → Guest Cart → Checkout (or the cart's checkout stage) → Order Confirmation → Shopper Account (both Signed-In and Signed-Out states) → Store Policies (shipping & returns, standardized against Shopify/WooCommerce/BigCommerce/Google Merchant Center), each at the site's own route. Each surface round explores the page's composition at desktop width, not only its colour and type. A page that keeps the old layout under new tokens is restyled, not redesigned.
     3. **Global Chrome & Discovery:** Shared header and footer, built from the site's own components (where any theme or preset switcher sits is a grill decision) → Search (EmDash's `<LiveSearch />`, plus a results page if the site needs one). A search that appears in a chosen design ships as a working, labelled text input wired to real results. An icon or link that only opens a search page is not a search control. The results page covers an empty query, no results (with a next step) and results that link to real routes. Where search sits is a grill decision.
   - **Choose When to Build:**
     - **Live grill** (the user picks each candidate, and the session has no fixed time or generation budget): lock every surface on the checklist before codebase implementation or long test runs, unless the user asks for a checkpoint PR.
     - **Time- or budget-capped, or unattended run:** build as you go. (1) Translate the locked foundations (layout, palette, type) into `tokens.css` and `design.md`, and wire every route to them, naming any route that needs a special write path. (2) Implement each later surface's selection in source before opening the next surface's round. (3) Record any surface that is decided but not built as "selected, not implemented". (4) Before the first generation, write a budget plan (for example `.stitch/plan.md`) that assigns the run's whole generation budget (the cap or credit share set for it, or what its time limit allows) to named rounds in checklist order: generations for layout exploration and for each surface round, none for palette and type (deterministic uploads, item 1). Size each round's candidate count so every planned round fits, and keep a running tally. Do not frame the budget as something to conserve, and do not replace surface generations with hand-authored HTML: that leaves budget unspent and surfaces unjudged. (5) Before opening each round, check that the remaining time covers implementing it, verification and the records; if not, stop opening rounds and style the remaining surfaces from the foundations. At closeout, report generations spent against the plan and rounds judged against rounds planned, from the tally. In such runs, locking everything first tends to leave chosen surfaces unbuilt when the budget runs out.
     - **In either mode, a surface is done only when it is** *selected* (every candidate's screen ID, the selected ID and the reason are in the decision record), *implemented* (the record names the source files), *framed* (the route renders inside the shared header and footer and takes colour, type and spacing from tokens, with no hard-coded colours outside test-pinned values) and *honest* (its empty, error, closed and unsupported states render truthfully). Wire every public route to the shared frame before deepening any one surface. A route left on old styles breaks the store more than a simpler layout on a framed route. Give every checklist surface exactly one status, worded identically in `design.md` and in every report that lists surfaces: `selected, implemented` · `selected, partly implemented: <what is missing>` · `selected, not implemented` · `no round judged; styled from foundations only`. A surface whose candidates nobody inspected is never `selected`.
   - When holding locked variables constant, upload deterministic HTML variants via `stitch upload screen <file> --route <route> --title "<title>" --project <id> --json` or `stitch_upload_file` (`screens:batchCreate`) so Stitch renders pixel-accurate screenshots in ~2s without mutating locked DOM structure, and download artifacts with `stitch download screen <screen-id> --project <id> --html --image --output <dir>` (or `stitch_download_screen` with `width: 2560`). Use `stitch url project <id> --json` or `stitch serve -p <id>` when sharing or previewing screens locally.
   - **Tiebreaker & Hybrid Rounds:** When the user is torn between two candidates (e.g., likes one candidate's page frame with another's product cards), immediately generate a 2–3 screen **Tiebreaker / Hybrid** round in real page context so the user can compare the exact combination before locking.
   - **Show Every Candidate as a Desktop + Mobile Pair:** At each grill decision, put each candidate's desktop screen next to the same design rendered at a 390 px viewport. The mobile view re-renders the screen's own HTML and costs no Stitch generation. Storefront choices usually break on mobile first: the nav, hero type scale, grid density, cart controls and tap targets.
   - **Check Each Candidate Against the Real Page Before It Locks:** compare its text with the captured route and strip whatever the page does not have: badges, counts not computed from the rendered data, ratings, reviews, stock levels, shipping or policy promises, payment logos, steps that do not exist, invented product copy, order numbers. List what you stripped in the decision record, and prefer candidates that need no stripping.
   - **Optional Mobile Pass After Each Desktop Lock:** Once a surface's desktop direction locks, offer one mobile-specific pass for what a narrow render can't fix: the nav pattern, a sticky add-to-cart, tap targets and dense tables. Lock mobile separately and record both locks. Skip the pass if the user declines.
   - **Lay Out the Canvas as Named Groups, One Row per Round or Surface:** Keep each round or surface (home layout, palette, type, then each storefront page) in its own canvas row of at most about 10 frames, in round order, like a contact sheet. Wrap each row in a named canvas group (for example `R2 · Palette` or `S3 · Cart`, plus the locked candidate once it locks) so the user can follow the grill on the canvas. Stitch itself appends every frame to one long row, so re-flow and regroup after each round as described in [references/grilltrack-visual-cycle.md](references/grilltrack-visual-cycle.md).

4. **Handle Unbuilt Code / Plugin Gaps Without Losing UI Momentum:**
   - If the user requests a UI control, interaction, or workflow during the design grill that is not yet supported by the underlying EmDash site code or companion plugin (for example, per-variant quantity steppers, multi-variant batch add on a PDP, or structured policy highlight fields):
     1. **File an issue immediately** (`gh issue create --label smoky-agent`) on the relevant repository documenting the gap and desired contract (creating the `smoky-agent` label first if missing). File issues only for capabilities the code or plugin lacks. An optional feature you chose not to ship is a design decision: record it in `design.md`, not as an issue. Stitch and other tooling limits are not site gaps; note them in the closeout report. Cite an issue or PR number only when a tool output, file or page read in this session names it.
     2. **Mock the feature cleanly in the Stitch design** so the visual system and layout hierarchy account for the real UX. The mock stays in Stitch. In source, omit the control, or show it unavailable with a text reason, as plain text or a native `disabled` control that looks unlike every enabled action on the site (fill, outline, weight). Never ship a control that looks like it works and does nothing.
     3. **Keep moving on the frontend/UI design grill**—never get sidetracked implementing backend or plugin feature additions mid-design.

5. **Align with Upstream EmDash Theming & the Composition Primitives:**
   - Read [references/grilltrack-visual-cycle.md](references/grilltrack-visual-cycle.md) before modifying Astro/EmDash components.
   - **Upstream EmDash Theming (`src/styles/tokens.css` + `src/styles/theme.css`):**
     - Define all design tokens inside `@layer base` in `src/styles/tokens.css` using CSS `light-dark(<light>, <dark>)`, and ship a blank unlayered `src/styles/theme.css` (`:root {}` with adopter comments) imported after `tokens.css`.
     - **Real Live Store vs. Starter / Playground Showcase:** A live production storefront locks **one** chosen brand palette in `src/styles/tokens.css` (an optional `Light` / `Dark` / `System` appearance toggle is fine). Only starter templates, demo playgrounds, or staging sites meant to show prospects several colorways keep 2–3 curated palettes as `:root[data-preset="..."]` blocks with a preset switcher. The switcher's look and placement are grill decisions for that site; never duplicate it in both header and footer.
   - **EmDash Composition Primitives (`blocks`, `sections`, `widgetAreas`):**
     - Use the site's existing page-layout blocks, reusable sections, and widget areas. Keep their names and seeded content, including legacy sections that migrations or tests still read.
     - Add a primitive only where owners need to edit that content in the CMS: a `pages.layout` block for an owner-arranged page, a Portable Text section (`getSection()` + `<PortableText />`) for copy reused across pages, or a widget area (`<WidgetArea name="..." />`) for an owner-managed region.
     - EmDash search needs `"search"` in the collection's `supports`, `"searchable": true` fields, and `<LiveSearch>` from `"emdash/ui/search"`.

6. **Prove on Desktop and Mobile & Archive the Locked References:**
   - **Keep the Decision Record Complete:** in `design.md`, beside the GrillTrack ledger, write one row per round or surface: round · variable · every candidate's full screen ID · selected full ID · why, plus content stripped · status · implemented in (file paths). Never shorten an ID. When the record replaces an older section that still promises a later decision, mark that section superseded, with the date, in both places.
   - Run the repo's own full verification across desktop and mobile viewports (DinkusKit storefronts: `bin/verify-web quick` and `bin/verify-web full`, i.e. `pnpm verify`) after the last source edit. A build plus unit tests is not enough: the full run includes text, format and lint audits, and a failing audit can stop the browser tests before they run. In a capped or unattended run, also run it once the foundations and every route are wired, while there is time to fix failures. Keep each edited file in the repo's existing format (indentation, final newline; in seed or config JSON change only the keys you need). List any edit made after the last full run as unverified.
   - **Before Closeout, Check Each Named Defect Mechanically:** every public route renders inside the shared frame and token layer (list the routes and check each one's import); components have no hard-coded colours outside test-pinned values; every empty state links onward; every selector that sets `display` on an element the code toggles with `hidden` is followed by its own `[hidden] { display: none }` rule (search scripts and markup for `hidden` to list those elements); every closed or unsupported action reads as unavailable, not enabled; no shopper copy comes from CSS `content:` or from markup that EmDash or Commerce did not supply, and no page has developer notes; every header and footer label works or reads as plain text; no decision-record ID contains `…`, every row has a status and implemented-in, each surface's status matches across records, and stale sections are marked superseded. Report each check with its real output. A check that could not run is reported as not run, with its error, never as a pass.
   - Archive the locked Stitch `.html` source files, `=w2560` `.png` screenshots, `.stitch/DESIGN.md`, `design.md`, and `tokens.css`/`theme.css` in the project's design-asset archive (DinkusKit: `dinkuskit/dinkus-pr-assets`, `<repo>-stitch-<pr>/`) so future implementation and review agents have both visual and HTML/CSS reference truth.
