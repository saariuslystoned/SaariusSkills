# Puppet v0.2 fast-launch slice

Status: v0.2 fast launch and explicit checkpoint collection are
subscription-backed and live-proven across all five harnesses. The transport
baseline remains bound to `f89bbed426f5dea1e6d3ab5128b5a01e6d42eb27`;
the final receipt-and-current-byte-bound replay and exact-halt proof is bound to
`1c0d9f3cf30813ea91447fa0b5822c15b6c843ee`.

## Operator outcome

An operator may explicitly select any one-to-five-target mix from AGY, Codex,
Claude, Cursor, and Grok in one `puppet_launch.py run` request. The request names
one warm catalog, clean source/head, task input, fresh launch ID, campaign root,
worktree parent, explicit effect modes, and—when a multi-target request can
mutate—one exact selected mutation owner. Puppet then:

- allocates each selected worktree serially against the shared Git metadata;
- compiles all selected exact ordinary-run plans concurrently;
- verifies every plan, controller, artifact, warm qualification blocker set,
  worktree, run root, profile root, campaign, and command vector;
- recompiles all plans behind a global read-only barrier before starting any
  harness;
- launches only the selected exact v0.1 controllers in isolated child sessions;
- emits immediate target-labeled progress instead of remaining silent;
- preserves active siblings when a post-barrier lane fails;
- reconciles every failed submitted launch with exact read-only status;
- refreshes attach tickets or opens native read-only TUI views only after all
  launches settle;
- supports concurrent status, attach, view, explicit bounded source-checkpoint
  collection, and exact halt for the same plan set; and
- binds the result to every plan hash, the plan-set hash, the fanout script,
  adapter, protocol, and v0.1 controller identities.

`prepare` materializes the same campaign without launching. `status`, `attach`,
`view`, `checkpoint`, and `halt` accept that one exact create-only campaign
manifest, so the operator no longer has to reconstruct or paste one command per
lane. Checkpoint collection is always an explicit post-launch request; an
ordinary run never asks the agents to stop or hand off.

## Warm catalog boundary

`catalog-init` is a one-time binding step after qualification. It concurrently
verifies the supplied qualified manifests and records their exact shared
campaign/goal/controller authority, adapter/protocol identities, and stable
private profiles. The body-free catalog is mode-0600, create-only, and
fingerprinted. It never qualifies a harness, logs in, or inspects an auth store.

An ordinary `prepare` or `run` validates that catalog but never invokes census,
onboarding, login, probe, pairing, or qualification. It separately binds the
current clean source/head and task-input hash. The catalog is not a transferable
authorization certificate; `run` still requires `--allow-live-launch`, and the
single-target controller still revalidates its narrow body-free login and exact
runtime identities immediately before launch.

## Safety boundary

The launcher and coordinator are additive and remain outside the v0.1 adapter
implementation fingerprint. They cannot probe, qualify, onboard, log in, route
targets automatically, add native slash commands, or halt a successful sibling.
Existing single-lane controllers retain auth, source, process, tmux, delivery,
checkpoint, and exact-halt authority.

The launcher rejects `run` without `--allow-live-launch` before creating
anything. It uses new IDs and roots, publishes catalogs/contracts/plans/campaigns
create-only, and records progress in an atomic body-free preparation state.
Worktree creation is deliberately serialized; plan compilation and harness
execution are concurrent. A partial preparation records
attempted, created, and ambiguous worktree identities with
`automatic_cleanup: false`; it preserves exact worktrees and artifacts for
adjudication rather than deleting or guessing. Only one selected lane may own
mutation. Every support lane receives only the explicitly requested
`read`/`test` intersection; Puppet never silently adds a support mode.

Each controller child has a 120-second deadline. On expiry, the coordinator
sends SIGINT only to that exact child and waits 15 seconds for controller cleanup.
It then uses bounded TERM/KILL fallback only on that lane's isolated owned process
group and reports `recovery_required`. Operator Ctrl-C sets a shared cancellation
event; every exact child gets a shorter five-second cleanup window before the
same owned-group fallback, so executor shutdown is bounded by cleanup rather
than the 120-second controller deadline. Children are placed in separate
sessions so terminal signals are never broadcast to unrelated processes.
Queued children do not start after cancellation, and repeated Ctrl-C is
idempotent while the recovery receipt is assembled.
Child pipes are drained continuously with a 1 MiB in-memory cap per stream.
Aggregate results contain only action-specific projected fields and stable
error categories, never raw controller objects or arbitrary error/detail text.
Pipe-holding descendants cannot pin cleanup, including descendants outside the
owned process group; their output fails closed without cross-thread pipe close.

## Verified here

- Catalog initialization rejects source-only manifests, verifies every selected
  qualification, binds body-free identities, and cannot overwrite an existing
  catalog.
- Campaign preparation rejects dirty or drifting sources, stale artifacts,
  missing catalog targets, duplicate modes, branch collisions, and overlapping
  ownership before launch.
- Any explicit one-to-five-target mix compiles through the same command surface;
  `all` produces five isolated lanes.
- Git worktree creation is serialized while plan compilation overlaps.
- Failed partial preparation preserves the exact completed worktrees and marks
  automatic cleanup false.
- `run` requires explicit live acknowledgement and hands the complete exact plan
  set to fanout once; later lifecycle commands recover that set only from the
  fingerprinted campaign.
- Five launch callbacks overlap behind a deterministic barrier.
- A runtime failure remains lane-local and never invokes halt.
- Invalid roots include the full cross-lane worktree/run/profile product.
- Proof and state roots remain exactly `run/proof` and `run/state`.
- Canonical `--json` controller argv and macOS lexical paths round-trip through
  one genuinely compiled operator-plan v1 packet.
- Source-only, target-gated, stale, or otherwise extra-blocked plans are not
  admitted as warm launches.
- Attach/view failures are visible separately from launch success.
- Failed submitted launches receive exact status reconciliation and recovery
  commands.
- Uncertain halts receive the same read-only reconciliation without automatic
  retry.
- Initial launch attach commands are omitted after a slow batch; the refreshed
  `viewer.result` is canonical.
- Attach supervision is bounded to 13.25 seconds end to end, below the
  controller's 30-second ticket TTL, so a stalled sibling cannot make a
  reported attach command stale.
- Validated launch-incomplete blocker metadata identifies the narrow Grok
  dead-lease candidate without retaining cleanup error text.
- Forbidden body-shaped child JSON is rejected; unrecognized successful fields
  and arbitrary failure error/detail text are never re-emitted.
- Oversized child streams are continuously drained, bounded in memory, and
  rejected without a disk-growth or pipe-backpressure failure mode.
- Ctrl-C actively cancels exact isolated controller children and emits a
  structured recovery receipt after bounded cleanup.
- Lifecycle fanout targets only the selected exact state-root/session pairs.
- Explicit checkpoint collection creates an exact body-free assignment per
  lane, submits all live lanes concurrently, polls only their bound private
  mode-0600 output files, imports through the existing controller, and confirms
  the structural checkpoint without reading a pane.
- A checkpoint timeout, malformed output, or stale output remains lane-local;
  a create-only post-send delivery receipt distinguishes a real retry from a
  pre-send stale file, and replay rehashes current checkpoint bytes before
  returning an already-imported checkpoint. Collection never automatically
  reviews, accepts, halts, exits, deletes, or retries a target.
- The fanout script does not change adapter, protocol, or target instruction
  qualification fingerprints.
- Plugin metadata advances from 0.1.0 to 0.2.0.

  42,277 ms.

  identity and a claimed native-view ticket.
- Exact halt of all five owned process trees completed in 4,776 ms; every final
  session state was `HALTED`, every halt sent its exact signal, and tmux audit
  state was preserved.
- Per-lane launch elapsed time was AGY 20,328 ms, Codex 27,625 ms, Claude

## Deferred follow-ons

1. Add a controller-attested reusable qualification certificate that separates
   stable harness/profile proof from current task authorization. Never obtain a
   cache hit by deleting the present campaign/goal comparisons.
2. Consider an event-loop supervisor only if live latency measurements show
   the bounded thread supervisor itself is material.
3. Separate the immutable Puppet supervisor checkout from an arbitrary target
   repository. The current fast path deliberately requires the launcher,
   fanout, CLI, and campaign source to share one exact clean Git worktree; it
   does not yet support cockpit-to-unrelated-repository launch campaigns.
